# CLI daily-driver evaluation and implementation plan

## Context

Aveli must become a CLI-first daily browser driver that is measurably faster and less labor-intensive than agents operating a visible browser. It must cover authenticated read workflows, general office workflows, and consequential actions, while avoiding repeated login: a user signs into a dedicated managed Chrome profile once, including MFA, and later CLI runs reuse that profile without exposing credentials to either model. The current indexed-DOM loop is a useful base, but `aveli` currently launches the inspector, production profiles are intentionally ephemeral, supported actions are limited to the top document, and the existing speed evidence covers only a small public-web sample. The end state is therefore a managed-profile CLI plus typed multi-context actions, explicit artifact transfer and semantic side-effect policy, independent verification, and a matched corpus that decides whether it qualifies as the daily driver.

## Approach

### 1. Freeze an executable comparison contract before expanding capability

1. Add `browser-use==0.13.10` to a new `benchmark` dependency group in `pyproject.toml`; keep it out of the runtime dependencies. This exact release exposes `Agent(task, llm, browser_session, use_vision, max_actions_per_step, ...)`, `Agent.run(max_steps=...)`, and `BrowserSession(cdp_url, headless, user_data_dir, allowed_domains, keep_alive, viewport, ...)`. Update `uv.lock` through the normal `uv lock` flow during implementation.
2. Add the benchmark package `benchmarks/` with these exact authored files; no equivalent reusable corpus/adapter layer exists in the repository:
   - `benchmarks/contracts.py`: immutable `EvaluationCase`, `DriverRun`, `VerifierResult`, `DriverAdapter`, and the failure enum `unsupported_control`, `authentication_required`, `policy_denied`, `stale_page`, `provider_failure`, `browser_failure`, `timeout`, `verifier_failed`, `application_defect`, `harness_error`.
   - `benchmarks/adapters/aveli.py`: invoke `aveli run` as a subprocess and parse its one JSON result.
   - `benchmarks/adapters/browser_use.py`: run the Browser Use 0.13.10 Python API directly, not its interactive CLI: construct `BrowserSession(cdp_url=<managed fixture profile endpoint>, allowed_domains=["127.0.0.1"], keep_alive=True, viewport={"width": 1120, "height": 780})`; construct `ChatOpenAI` from `BENCHMARK_MODEL`/`OPENAI_API_KEY`; construct `Agent(task=case.goal, llm=llm, browser_session=session, use_vision=False, max_actions_per_step=1)`; call `await agent.run(max_steps=case.max_actions)`; then run the same independent verifier used for Jev. The adapter records Browser Use package/model settings and never treats `history.final_result()` as success.
   - `benchmarks/verifiers.py`: registry `VERIFIERS: dict[str, OutcomeVerifier]` containing every verifier ID named below; unknown IDs fail before either driver starts.
   - `benchmarks/corpus.json`: the complete case list with fixed goal, start path, fixture reset name, capabilities, verifier ID, timeout, and action budget.
   - `benchmarks/run.py`: reset/seed fixtures, clone the profile seed, alternate adapter order, retain every attempt, invoke verifiers, and write `runs.jsonl` plus `summary.json`.
   - `benchmarks/report.py`: generate success, failure-class, intervention, cost, p50/p95, paired-ratio, and bootstrap-confidence tables from retained runs only.
3. Define the contracts exactly as `EvaluationCase(case_id: str, tier: Literal["fixture", "authenticated"], app: Literal["controls", "dashboard", "docs", "tickets"], start_path: str, goal: str, capabilities: tuple[str, ...], reset_fixture: str, profile_fixture: str | None, verifier_id: str, timeout_seconds: float, max_actions: int)` and `DriverRun(case_id: str, driver_id: Literal["aveli", "browser-use-0.13.10"], attempt: int, status: str, failure_class: str | None, wall_ms: int, startup_ms: int, first_observation_ms: int, core_loop_ms: int, verification_ms: int, model_ms: int | None, browser_ms: int | None, actions: int, decisions: int | None, stale_decisions: int | None, tokens: int | None, billed_cost: str | None, human_interventions: int, evidence: tuple[str, ...])`. The primary interval is adapter invocation through verifier completion; component timings are secondary and must sum to wall time.
4. Add a deterministic loopback fixture service in `benchmarks/fixtures/server.py` using Python's standard-library HTTP server plus in-memory state protected by one lock; no database or framework is needed. `GET /health` reports readiness, `POST /api/reset/<fixture>` resets one case, and `GET /api/state/<fixture>` is the authoritative verifier read model. Start it with `python -m benchmarks.fixtures.server --port 0 --state-dir <temp>`; print one JSON readiness line containing `base_url` and write no credentials.
5. Add four exact fixture applications under `benchmarks/fixtures/static/`:
   - `controls.html`: top-document navigation, text/autocomplete, checkbox/radio/switch, duplicate-label native select, keyboard modal, popup, same-origin frame, a second loopback origin for the cross-origin frame, nested scrolling, upload, and download. Server routes expose stable reset/state endpoints; verifier IDs are `controls.navigation.v1`, `controls.form.v1`, `controls.keyboard.v1`, `controls.popup.v1`, `controls.frames.v1`, `controls.scroll.v1`, `controls.upload-sha256.v1`, and `controls.download-sha256.v1`.
   - `dashboard.html`: synthetic login cookie `aveli_fixture_session`, report table, build/release state, and a generated download. Verifier IDs are `dashboard.account.v1`, `dashboard.report.v1`, `dashboard.release.v1`, and `dashboard.download.v1`.
   - `docs.html`: authenticated documentation search with pagination plus same-origin/cross-origin frames and a reference popup. Verifier IDs are `docs.search.v1`, `docs.pagination.v1`, `docs.frame-result.v1`, and `docs.popup-reference.v1`.
   - `tickets.html`: authenticated ticket search/detail, non-consequential tag update, fixture upload, and consequential `close`, `delete`, and `approve` controls carrying stable `data-aveli-effect` and `data-aveli-record-id` metadata. Verifier IDs are `tickets.open.v1`, `tickets.tag.v1`, `tickets.upload-sha256.v1`, `tickets.close.v1`, `tickets.delete.v1`, and `tickets.approve.v1`.
6. Add `benchmarks/fixtures/profiles.py seed --base-url URL --output DIR` to create a dedicated managed profile, set only the synthetic fixture session cookie through the fixture login route, close Chrome cleanly, and write `profile.json` with the base URL and seed digest. Each paired attempt clones this seed into separate Aveli and Browser Use temporary `user_data_dir` paths so attempts cannot contaminate one another. The checked-in corpus contains no real credentials, customer data, CAPTCHA, or MFA.
7. Put exactly 30 cases in `benchmarks/corpus.json`: the 8 control cases above, 4 dashboard cases, 4 docs cases, 6 ticket cases, plus 8 additional parameter-distinct fixture states covering dynamic autocomplete, date selection, grid filtering, stale frame replacement, popup navigation, expired session, denied consequential proposal, and changed-after-approval proposal. Every case names one reset fixture and one verifier; unsupported behavior is retained as a classified result, never excluded.
8. Generalize the existing instrumentation in `scripts/measure_flights.py` into the adapters without rewriting or deleting the historical Flights artifacts. Retain every attempt and record driver source/version, model ID/settings, browser version, corpus hash, verifier module hash, fixture server revision, and profile-seed digest.
9. Run 10 paired repetitions for each of the 30 cases in alternating driver order, yielding exactly 600 retained attempts. Both adapters use the same goal, fixture reset, cloned authenticated seed, 1120×780 viewport, action budget, timeout, verifier, local Chrome major version, and `BENCHMARK_MODEL`. Use `OPENAI_API_KEY` only for Browser Use and the existing TypeSafe/text-provider keys only for Aveli; report billed costs separately because the model stacks differ. Do not compare CDP-call counts across drivers.
10. Real applications are a post-fixture shadow corpus, not an implementation prerequisite. Add `benchmarks/shadow.example.json` documenting the same case schema with placeholders only; do not claim real-world daily-driver readiness until owners provide actual non-production URLs, synthetic accounts, reset operations, workflow policies, and authoritative verifier endpoints.
### 2. Replace the inspector-first command with a direct task CLI and persistent managed profiles

1. Change `pyproject.toml` so `aveli` targets a new `aveli.cli:main`; preserve `aveli-internal-worker = "aveli.worker:main"` unchanged and expose the inspector as `aveli demo`.
2. Add `aveli/cli.py` with these exact command shapes:
   - `aveli profile open --profile NAME --url URL`: start the named profile visibly so the user can complete login/MFA once.
   - `aveli profile status --profile NAME`: report stopped/running, Chrome PID ownership, CDP reachability, and profile path without printing cookies or browser storage.
   - `aveli profile stop --profile NAME`: stop Chrome and Browser Harness gracefully while preserving profile data.
   - `aveli run --profile NAME --url URL --goal GOAL [--goal GOAL ...] --workflow WORKFLOW --output PATH`: run without the inspector, emit one JSON result to stdout, write detailed evidence under `PATH`, and return nonzero unless independently verified.
   - `aveli demo --profile NAME`: run the existing inspector only when explicitly requested.
3. Add `aveli/profile.py` with `ProfileConfig.from_env(name, environment)`, `ManagedProfile.ensure_running(*, visible=False, initial_url="about:blank")`, `ManagedProfile.connection_environment()`, `ManagedProfile.status()`, and `ManagedProfile.stop()`. Store profiles under `${AVELI_PROFILE_ROOT:-~/.config/aveli/profiles}/<name>/{chrome,harness-runtime,harness-tmp,chrome.log,process.json}` with directories mode `0700`.
4. Reuse Chrome discovery, random loopback CDP startup, `DevToolsActivePort` readiness, process-group termination, and Browser Harness environment setup from `aveli/isolation.py`, extracting shared private helpers only where both lifecycles use identical behavior. Do not add persistence flags to `IsolatedChrome`: it must keep creating/deleting an ephemeral profile and `ProductionRunner` must continue requiring `_ACTIVE_ISOLATION`.
5. Launch a managed profile with `--remote-debugging-address=127.0.0.1`, `--remote-debugging-port=0`, `--user-data-dir=<profile>/chrome`, `--no-first-run`, and `--no-default-browser-check`. Derive stable `BU_NAME`, `BH_RUNTIME_DIR`, and `BH_TMP_DIR` from the profile and set `BU_CDP_URL` from the live `DevToolsActivePort`; this removes recurring Chrome remote-debug approval from routine runs.
6. Serialize startup with a per-profile lock. Reuse a process only after verifying its stored PID/start fingerprint, live CDP endpoint, and matching profile ownership. Reject ambiguous ownership instead of attaching to or killing an unknown process. `stop()` removes stale runtime/process metadata but never profile data.
7. Preserve import ordering: `cli.py` must parse configuration, ensure the profile, and install the `BU_*`/`BH_*` environment before lazily importing `Agent`, `Browser`, `demo`, or `browser_harness`. Delete `examples/run.py` once `aveli run` covers its URL/goal behavior; keep task-specific examples only as evidence/verifier examples.
8. On a clean/expired profile, recognize the configured workflow's login boundary and return `authentication_required` with the exact `aveli profile open ...` remediation. Do not ask the text model to generate passwords/MFA values and do not automate login in this milestone. Profile A must never satisfy a run requesting profile B.

### 3. Replace cross-module action dictionaries with typed browsing-context contracts

1. Before adding operations, introduce parsed Python contracts for `ObservedPage`, `ObservedAction`, `BrowsingContextId`, `Decision`, `PreparedAction`, and `ExecutionResult`. Preserve the current single-request TypeSafe choice: operation plus operation-specific compatible targets; never let the model emit selectors, coordinates, paths, scripts, or arbitrary key strings.
2. Update the action pipeline in order: `snapshot.js` returns the wire representation; `browser.py:Browser.observe` parses it; `model.py:action_space` and `choose` expose compatible targets; `agent.py:Agent.command` carries the selected typed action; `job.py:classify_action` and `PreparedAction.from_proposal` freeze it for policy/audit; `browser.py:Browser.act` performs freshness checks and execution. Migrate every caller and delete the old mutable-dictionary path in the same change.
3. Include target/tab, frame, and document identity in observed actions, decisions, freshness guards, audit records, and execution results. A stale action must never cross a replaced frame, navigation, tab, or focused widget.
4. Keep `Agent` as the use-case orchestrator; move prediction, terminal transition, text preparation, mutation, and observation into focused methods rather than adding pass-through layers or more action-kind branches to the current monolithic flow.

### 4. Add multi-context navigation and bounded office-work operations

1. Frames: continue using the per-document reader in `snapshot.js`, but have `Browser.observe` enumerate eligible frame execution contexts and merge their controls while preserving `frame_id` and document identity. Execute and freshness-check in the exact selected frame. Include frame name/origin only when necessary to disambiguate otherwise identical controls.
2. Popups/tabs: enable flattened target auto-attach in `Browser.__init__`, maintain an owned-target registry, and select the active target deterministically after an opener creates a popup. Include opener/target identity in observations and actions. Before continuing in a popup, production policy must approve its host; close or deny undeclared-host targets without further mutation. Support explicit return/close of an owned popup.
3. Keyboard: add a bounded `PRESS_KEY` action and `ActionClass.KEYBOARD`. Offer only code-owned keys appropriate to the observed focused widget: `Enter`, `Escape`, `Tab`, `Shift+Tab`, arrows, `Home`, `End`, `Space`, `PageUp`, and `PageDown`. Never accept model-generated key names or text. Bind focus identity into freshness checks and emit complete key-down/key-up sequences.
4. Scrolling: retain top-window scroll and add observed scroll-container targets with current scroll bounds. The model selects from compatible container targets; execution scrolls that exact container and verifies movement or a stable end boundary. Do not add coordinate-generated scrolling.
5. Generalize the operation model and job schema in one clean versioned cutover; reject old/new ambiguous payloads rather than silently translating them. Update `snapshot.js`, `model.py`, `agent.py`, `job.py`, `runner.py`, audit output, and all callers together for each new action.

### 5. Add explicit, verified uploads and downloads

1. Downloads: preserve `ActionClass.DOWNLOAD`, but make download completion a first-class execution result. Allocate a run-scoped directory before clicking, consume CDP begin/progress events, and return filename, size, MIME when available, and SHA-256. Timeout/cancellation or a missing expected digest is failure; a click receipt is never success. Managed profile cleanup must not delete an approved output artifact.
2. Uploads: observe file inputs without exposing local paths or file content. Add `ActionClass.UPLOAD`; the job/workflow binds a reviewed alias to an immutable local artifact digest, while the model chooses only the observed field and alias. The executor uses that exact observed field plus exact alias-bound artifact. Hidden/styled, replaced, disabled, disallowed, or digest-mismatched inputs fail before mutation.
3. Keep transfer paths/content out of model requests, screenshots, and audit payloads. Require explicit workflow policy for uploads and code-owned verifiers for both transfers. Do not add drag-and-drop or arbitrary file browsing until the corpus contains a justified case.

### 6. Add workflow-bound semantic policy for consequential actions

1. Extend the production policy from mechanical control classes to versioned workflow definitions. Each workflow identifies exact allowed hosts, model/provider IDs, allowed data classes, permitted action classes, stable application metadata used to identify consequential controls, allowed artifact aliases, verifier ID/version, and whether terminal approval is required.
2. Keep unknown controls denied. A JavaScript `Delete`, `Send`, `Approve`, purchase, booking, account, or production-mutation control must not inherit broad `interact`; bind its declared business effect to stable application-owned metadata such as reviewed test IDs plus page/workflow context. Do not infer consequential semantics solely from visible labels.
3. For a consequential proposal, freeze `workflow_id`, `job_id`, page fingerprint, browsing-context identity, observed node identity, business effect, destination/record summary, generated content digest, and expiration. Present that immutable proposal in the terminal and require an explicit yes/no response at the point of risk. Any changed page, target, content, or expired proposal requires a new prediction and approval; approval is never a prompt instruction.
4. Execute an approved mutation at most once, audit `action_executing` before input, and never retry. Verify the authoritative effect through the workflow's application API/read model when available; DOM-only checks are permitted only for explicitly read-only/non-consequential cases. A model `DONE`, successful click receipt, or matching page text alone cannot verify a consequential outcome.
5. Bind external-data approval to workflow, exact hosts, providers, and allowed data classes rather than the current global `AVELI_EXTERNAL_DATA_APPROVED` flag. Authenticated page text, URLs, labels, and values sent to providers must be explicit in the workflow. Credentials, cookies, tokens, signed URLs, local paths, and file contents remain prohibited.

### 7. Make final outcomes fresh and independently verifiable

1. Add `OutcomeVerifier` to `aveli/runner.py` with `verify(page: ObservedPage, evidence: tuple[ExecutionEvidence, ...]) -> VerificationOutcome`. Keep `VerificationSpec` as the declarative URL/title/text implementation for simple jobs. Add `aveli/workflows.py` with a `WorkflowRegistry` that loads authored workflow definitions and resolves exact verifier IDs; add fixture definitions in `benchmarks/workflows/{controls,dashboard,docs,tickets}.json`, each naming the stable hosts injected by the fixture runner, action/effect policy, artifact aliases, login path, and one verifier from `benchmarks/verifiers.py`. Unknown workflow or verifier IDs fail before browser startup.
2. Change `ProductionRunner.run(job)` to request a new observation after DONE; do not verify only `state["page"]`. Where an authoritative application API or database read model exists, combine it with browser state and artifact digests in the verifier result.
3. Emit machine-readable `JobResult`/CLI output containing status, failure class, elapsed/action counts, verifier ID/version, stable check IDs, final public URL form, and evidence digests. Never expose configured secret text, raw authenticated page content, cookies, credentials, or private artifact paths.
4. A direct `aveli run` that lacks an independent verifier must report `completed_unverified`, return nonzero, and never contribute a success to the benchmark or daily-driver gate.

### 8. Promote only after the evidence clears every tier

1. Evaluation harness gate: every case has an executable versioned verifier; every attempt is retained; deliberately wrong final states fail; all phase timings reconcile to wall time; rerunning one case with the same seed is deterministic; unsupported controls are classified instead of reaching DONE.
2. Authentication gate: a managed profile completes two consecutive authenticated CLI tasks with no login-page interaction or manual browser clicks; stop/restart preserves persistent cookies/local storage; clean and expired profiles return `authentication_required`; no password, MFA, cookie, token, signed URL, local path, or file content appears in model requests, stdout JSON, screenshots, or audit logs; concurrent writers to one profile are rejected.
3. Context/action gate: deterministic frame, popup, keyboard, nested-scroll, upload, and download cases all pass with zero stale cross-context mutations. Transfers pass only after digest verification. Keyboard actions come only from the code-owned allowlist.
4. Outcome/safety gate: zero false-positive verified outcomes across the deterministic corpus and audited representative runs; zero mutation retries, duplicate mutations, policy escapes, undeclared-host continuation, profile corruption, or unexpected consequential side effects. Production consequential controls remain denied unless the exact workflow semantic policy, terminal approval, and authoritative verifier are present.
5. Comparative gate: candidate verified success is at least 95%, no more than 2 percentage points below the interactive comparator overall, and no tier regresses by more than 5 points. Candidate end-to-end p50 must be faster; p95 may be at most 10% slower; the paired-bootstrap 95% confidence interval for median time ratio must support the published speed claim. Human interventions must be zero after profile setup for cases marked daily-driver-supported. Report warm authenticated startup/attach, core-loop, and verification times separately; never market loop-only timing as CLI wall time.
6. After comparative acceptance, shadow the intended internal workflows under the stronger existing production gate in `docs/internal-production.md`: at least 500 representative jobs over 14 days, at least 99% independently verified success, zero policy escapes/secret leaks/mutation retries/personal-profile attachments/orphan browsers, and reviewed samples for every non-verified status. This production gate supplements rather than replaces the comparative corpus.

## Critical files & anchors

- `aveli/isolation.py` — `ChromeConfig`, `IsolatedChrome.__enter__`, `_set_environment`, and `close`; source of reusable launch mechanics and the ephemeral production boundary that must remain intact.
- `aveli/browser.py` — `Browser.__init__`, `observe`, `fresh`, `act`, and `browser_operation`; owns target/frame context, freshness, input, popup handling, and transfer events.
- `aveli/snapshot.js` — authoritative observed control surface and node identity; must produce typed context-aware actions without selectors or executable model output.
- `aveli/agent.py` — `Agent.__init__`, `command`, `run`, and `close`; keep as orchestration while consuming typed actions and fresh verifier transitions.
- `aveli/job.py` — `JobSpec.from_dict`, `ActionPolicy.assess`, `classify_action`, `PreparedAction.from_proposal`, `VerificationSpec`, and `JobResult`; versioned policy/action/result contracts and semantic effect ownership.

## Verification

Run from the repository root. Fixture capability checks use local Chrome and the local fixture server; the matched comparison additionally requires `OPENAI_API_KEY`, `BENCHMARK_MODEL`, `TYPESAFE_API_KEY`, and `TEXT_MODEL_API_KEY`.

1. Run focused offline tests for profile name/path validation, process ownership and lock behavior, stopped/running/stale status, environment installation before lazy imports, typed action parsing, context-bound freshness, workflow/verifier registry loading, immutable approval proposals, output redaction, and verifier failure behavior.
2. Start the concrete fixture service with `uv run python -m benchmarks.fixtures.server --port 0 --state-dir <temp-state>` and read `base_url` from its readiness JSON. Seed auth with `uv run python -m benchmarks.fixtures.profiles seed --base-url "$BASE_URL" --output <temp-seed>`.
3. Run the managed-profile smoke against the dashboard fixture: `uv run aveli profile open --profile smoke --url "$BASE_URL/dashboard/login"`; complete the synthetic fixture login once; then run `uv run aveli run --profile smoke --url "$BASE_URL/dashboard" --workflow benchmarks/workflows/dashboard.json --goal 'Report the signed-in account and release status' --output <temp-output>` twice from separate processes. Expect `status: verified`, verifier `dashboard.account.v1`/`dashboard.release.v1`, and no visible-browser interaction on either routine run. Stop/restart and repeat to prove persistent cookie/local-storage reuse; call the fixture's expire-session endpoint and expect `authentication_required` with zero text-helper calls.
4. Run `uv run python -m benchmarks.run --drivers aveli --repetitions 1 --corpus benchmarks/corpus.json --profile-seed <temp-seed> --output <temp-smoke>`. Expect all implemented capability cases to verify and any not-yet-implemented operation to be exactly `unsupported_control`, never false success. Inspect authoritative fixture state to confirm frame, popup, keyboard, nested-scroll, upload/download digest, and stale-context outcomes.
5. Run the tickets consequential cases individually: denial must leave `GET /api/state/<fixture>` unchanged; approval must produce exactly one state transition and audit event; the changed-after-approval case must invalidate the proposal and perform zero mutation. These cases use `benchmarks/workflows/tickets.json` and verifiers `tickets.close.v1`, `tickets.delete.v1`, and `tickets.approve.v1`.
6. Validate verifier integrity by running `uv run python -m benchmarks.run --self-test-verifiers`; it deliberately corrupts every expected final state/artifact and must produce 30 verifier failures.
7. Run the full comparison with `uv run --group benchmark python -m benchmarks.run --drivers aveli,browser-use --repetitions 10 --corpus benchmarks/corpus.json --profile-seed <temp-seed> --output artifacts/benchmark-<date>`. Require exactly 600 JSONL attempt rows and a `summary.json` whose per-tier counts reconcile with raw rows; then run `uv run --group benchmark python -m benchmarks.report artifacts/benchmark-<date>/runs.jsonl` and confirm success, p50/p95, paired confidence interval, cost, interventions, and failure taxonomy for both drivers.
8. Run repository checks after behavioral proof: `uv run ruff check .`, `uv run pytest`, `node --check aveli/static/app.js`, `node --check aveli/snapshot.js`, and `uv build`.

## Assumptions & contingencies

- Authentication means user-performed one-time login/MFA in a dedicated Aveli-managed profile, followed by reuse while the site session remains valid. If a site keeps authentication only in tab-scoped/session state, keep the managed Chrome process alive; after restart, return `authentication_required` rather than automating credentials.
- Consequential tasks are supported only through versioned workflow policy, point-of-risk terminal confirmation, single execution, and authoritative verification. If stable semantic metadata or an authoritative verifier is unavailable, classify that task as `policy_denied`; do not fall back to visible-label inference or DOM-only success.
- Browser Use 0.13.10 with the Python adapter in `benchmarks/adapters/browser_use.py` is the sole comparator for the fixture gate. If its documented constructor or result API differs after dependency resolution, pin the last 0.13.x release exposing `Agent`, `BrowserSession`, `ChatOpenAI`, and `Agent.run(max_steps=...)`, update the lock and recorded driver ID to that exact version, and preserve the adapter contract; do not substitute an older Aveli commit.
- Managed local profiles and ephemeral production profiles remain separate lifecycles. If shared helper extraction would weaken `IsolatedChrome` cleanup or `_ACTIVE_ISOLATION`, duplicate the small launch helper instead of coupling production to persistent state.
