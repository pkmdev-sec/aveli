Current working tree review

Aveli is useful when choice is bounded.

The framework turns a page into a finite action set, lets a model choose, and keeps execution in code. That is a strong base for adaptive development checks. It is not a safe general-purpose browser worker yet.

Good fit

Development and staging checks

Use it for read-only smoke tests, UI journey reproduction, and exploratory acceptance checks with independent verification.

Not ready

Unattended consequential production work

Mechanical action classes cannot establish business intent. External approvals and soak evidence are also still open.

Prioritized review

Seven findings

Filter by severity. Each card separates the observed issue from the recommended change.

Showing 7 findings

High

F1. Policy classifies browser mechanics, not business effects

Most clicks become interact, even when page JavaScript deletes, sends, approves, submits, or navigates.

Observed

snapshot.js marks native links, downloads, and submits. job.classify_action treats other clicks as interact.

Recommendation

Do not allow broad interact on consequential pages. Add workflow-owned semantic effects or a stable control allowlist.

Evidence and impact
snapshot.js:63-67, job.py:251-269. A post-action host check cannot undo a same-host side effect. The CONNECT proxy restricts destinations, not business intent.
High

F2. Provider data approval is global

One environment flag enables provider transfer, but code does not bind approval to a workflow, host set, field set, or provider deployment.

Observed

Goals, URLs, titles, visible page text, labels, values, and recent generated text cross the provider boundary.

Recommendation

Deploy an immutable policy that names workflow ID, hosts, providers, and data classes. Reject jobs that do not match it.

Evidence and impact
model.py:105-145 and 152-198, config.py:49-73. Use synthetic accounts and non-secret data. A prompt rule is not a data-loss control.
Medium

F3. The proxy checks hostnames, not resolved addresses

An allowed DNS name can resolve to a private, loopback, link-local, multicast, or reserved address.

Observed

The proxy checks the requested hostname and then passes that name to socket.create_connection.

Recommendation

Validate resolved addresses and connect to an approved result. Keep platform egress policy as a second control.

Evidence and impact
network.py:23-35. Add DNS-rebinding and private-address tests before the worker can reach private networks.
Medium

F4. Exact model pinning is only partly enforced

The validator rejects names ending in latest. Other mutable aliases still pass.

Observed

The validation rule does not prove that a provider model or deployment ID is immutable.

Recommendation

Use provider-specific approved IDs. Record the provider-returned model ID in audit and result metadata.

Evidence and impact
config.py:21-25. Silent provider changes weaken reproducibility and make regressions harder to attribute.
Medium

F5. The central state machine uses implicit dictionary contracts

Page, action, decision, and history fields cross JavaScript and Python without a machine-checked schema.

Observed

Agent.command has AST complexity 29. browser_operation has complexity 17. New operations touch several modules.

Recommendation

Define typed cross-module contracts and split terminal, text, mutation, and observation transitions before adding browser features.

Evidence and impact
agent.py:66-181, browser.py:141-226. Tests contain the current risk, but frames, popups, uploads, and keyboard operations will multiply branches.
Medium

F6. The release candidate is not in a published Git revision

The branch still points at main. Production files, CI, tests, and deployment material are modified or untracked.

Observed

Local checks pass, but another checkout does not receive this worker and hosted CI has not exercised it.

Recommendation

Review and commit one coherent patch. Run hosted CI, build the image, and record its content digest.

Evidence and impact
Gate R5 is open. Data approval, procurement, workflow ownership, and 500-job soak evidence are also open external gates.
Low

F7. The runbook overstates final observation freshness

The runtime validates the stored page against a live semantic marker, then verifies the stored page. It does not take a new observation.

Observed

The check is useful, but the runbook calls it a "fresh observation," which is not the implemented mechanism.

Recommendation

Reobserve after DONE, or state that verification uses a freshness-validated stored observation. Add a race regression.

Evidence and impact
agent.py:107-114, runner.py:152-160, internal-production.md:11. Verification claims should describe the release boundary exactly.

Development use

Where the framework earns its cost

Strong

Adaptive preview smoke checks

Confirm that a deployed feature is reachable and visibly ready even when selectors or layout move.

Strong

UI journey reproduction

Replay a human goal against a known application revision and retain action history plus verifier evidence.

Strong

Exploratory acceptance checks

Use the agent to find a route through a changing interface. An engineer inspects failures and unexpected paths.

Conditional

Generated form input

Use only synthetic, non-secret values in a disposable environment. Put submit behind separate policy.

Conditional

Pull-request gate

Start as a non-blocking check. Make it required only after the team measures variance and false results.

Poor

Consequential production work

Payments, messages, deletes, account changes, and approvals need business-semantic authorization that is not present.

Poor today

Complex browser surfaces

Canvas, closed shadow roots, nested frames, uploads, popups, and arbitrary keyboard widgets are outside the action model.

Wrong tool

Deterministic test layers

Keep unit, API, component, accessibility, and visual-diff tests in purpose-built tools.

Local development needs a separate boundary. The production JobSpec rejects loopback and plain HTTP. Do not weaken that rule. Add a test-only isolated runner that permits local targets and blocks external egress.

Implementation path

Start with one read-only workflow

  1. Name the workflow.
    Use one preview-deployment check with an exact goal, host set, action set, and verifier.
  2. Use synthetic state.
    Create a disposable account or read-only page. Keep secrets and customer data out of provider context.
  3. Run one container per job.
    Preserve the current process ownership model. Do not turn the runner into a threaded multi-tenant service.
  4. Verify outside the model.
    Check visible state and, when possible, an application API or database read model.
  5. Collect shadow evidence.
    Record image digest, app revision, model IDs, result, action count, latency, cost, and failure class.
  6. Promote with measured criteria.
    Keep the check non-blocking until the workflow corpus shows stable verified results and acceptable cost.
